摘　要：小微轻食门店普遍缺一套用得起的点餐工具：菜单改不动、估清靠嘴说、下单后进入信息黑箱。本文设计并实现了一套面向此类门店的双端点餐系统，由微信原生小程序（生产端）、H5 页面（演示端）、商家后台与零第三方依赖的 Node.js 后端组成，四者共用同一套 REST 接口，业务逻辑只实现一次。系统在点餐链路之外增加了一个个性化套餐推荐模块：以 Mifflin-St Jeor 公式估算基础代谢，结合活动系数与目标系数得到单餐热量与蛋白预算，再在菜单的组合空间中做带约束的搜索，输出可解释的推荐结果；大模型仅用于文案润色且默认关闭，避免模型输出污染计算结果。开发过程采用意图驱动的 AI 协作方式：由人给出约束与验收标准，AI 产出实现，人负责取舍、复核与纠偏，全部迭代留有可检索的记录。系统共 33 次提交，通过 GitHub Actions 的语法检查、类型检查与接口冒烟，可在 10 分钟内本地复现。

关键词：轻食点餐；微信小程序；意图驱动开发；营养学模型；组合优化；可复现性

Abstract: Small light-meal stores usually cannot afford a full ordering platform: menus are hard to update, sold-out items are announced verbally, and customers lose visibility after placing an order. This paper presents a dual-front-end ordering system for such stores, consisting of a native WeChat Mini Program (production), an H5 page (demonstration), a merchant console, and a zero-dependency Node.js backend sharing one REST API. An additional module recommends personalized meal sets: resting energy expenditure is estimated with the Mifflin-St Jeor equation, activity and goal factors yield a per-meal calorie and protein budget, and a constrained search over menu combinations produces an explainable recommendation. A large language model is used only to polish the wording and is disabled by default, so generated text never contaminates computed values. The system is developed through intent-driven AI collaboration, with 33 commits, a passing CI pipeline, and a ten-minute reproduction path.

Keywords: light meal ordering; WeChat Mini Program; intent-driven development; nutrition model; combinatorial search; reproducibility

1　选题与问题定义

1.1 场景与用户

轻食门店的典型经营形态是：菜品 SKU 不多（20–40 个）、但每天要改价格、估清（售罄）、换图；顾客以写字楼与校园周边为主，通过手机下单、到店自取或短途配送。这类门店通常没有预算去接一套 SaaS 点餐系统，一个「能改菜单 + 能收单 + 顾客能看到进度」的最小系统就足以覆盖 80% 的日常。

因此本作品服务两类角色：

角色核心诉求典型动作
顾客快速看清今天有什么、热量多少、多少钱，下单后知道做到哪一步了选规格 → 加购 → 填地址 → 下单 → 看进度
店主 / 店员随时改价、估清、换图；新订单能听见看到，做完点一下登录后台 → 改菜品 → 看订单 → 接单 → 完成

1.2 三个具体痛点

不是泛泛的「餐饮数字化」，而是三个可验证的具体问题：

  1. 热量与价格信息不透明。轻食客群对「多少卡」的敏感度高于普通快餐，但多数小店只在小程序图片里贴一张模糊的营养表。本作品把 calorie 作为菜品一级字段，点餐页与购物车实时累计总热量（共 990 kcal），并在后台可按菜品维护。
  2. 估清靠嘴说。「今天牛油果没了」通常靠店员口头告知，线上仍可下单。本作品把 stock 落到菜品上：库存 0 时点餐页直接置灰并显示「已估清」，接口层也会在下单时二次校验并返回 409。
  3. 下单后进入信息黑箱。顾客不知道商家看没看到单。本作品让订单状态从「待接单 → 制作中 → 已完成」单向推进，并把状态事件链同步到顾客端跟踪页（5 秒轮询），商家一点「接单」，顾客页面上的进度条就会走。

1.3 目标与范围界定

维度本期做本期不做（及原因）
交易下单、金额重算、库存扣减、状态流转支付、退款、发票——需要支付资质与回调联调，个人赛周期内无法真实验证
履约商家接单 / 完成，顾客端可见骑手调度、路径规划——本项目不涉及真实配送体系，故不虚构骑手信息
账号商家单账号登录（Cookie 会话）顾客注册体系——顾客以「订单号」作为凭证查询，降低使用门槛
部署单机 Node 进程 + JSON 文件容器化、多实例、CDN——与「零依赖」定位冲突，列入后续规划

2.4 AI 个性化推荐：从身体指标到一份套餐

轻食用户最常问的两个问题是「我该吃多少」和「今天点哪个」。这两个问题可以被一个确定性模型回答，而不是每次调用大模型碰运气：

步骤做法
① 基础代谢Mifflin-St Jeor：10×体重 + 6.25×身高 − 5×年龄 + (男 5 / 女 −161)
② 每日消耗BMR × 活动系数（1.2 / 1.375 / 1.55 / 1.725）
③ 目标与蛋白减脂 0.8×、维持 1.0×、增肌 1.1×，并设热量下限；蛋白按体重 1.6 / 1.2 / 1.8 g·kg⁻¹
④ 单餐预算每日目标 × 40%（用户点的是"这一餐"，不是全天规划）
⑤ 组合搜索主菜(1) × 加料(0-1) × 汤/果汁(0-1) × 甜点(0-1)，约 1500 个候选
⑥ 目标函数蛋白达成 ×0.5 − 热量偏差 ×0.35 + 价格分 ×0.15 − 蛋白过量惩罚 ×0.2

几处取舍：蛋白质超过目标 1.3 倍开始扣分，否则算法会一路堆鸡胸；预算内无解时退化为「满足营养下限的最便宜组合」，并在结果里写出来；大模型只负责把结论写顺口，Prompt 里写死"不得改动任何数字"，没配 Key 时完全不参与。

模板：……这套组合合计 590 kcal、蛋白 55 g，热量偏差 +2%，蛋白达成 153%。
润色：……你这套组合合计 590 kcal、蛋白 55 g，热量只偏差 +2%，蛋白达成 153%，挺不错的，继续加油！
（11 个数字逐一比对一致；换成无效 Key 时 0.3 秒回落到模板文案，接口不受影响）
图 4　AI 定制页：指标 → 推荐组合 → 偏差与理由 → 一键加购

同样的输入必然得到同样的组合，没有随机数也没有模型采样，所以每一条推荐都能被复算。把推荐做成本地模型、只让大模型碰文案，原因就在这里。

3　意图控制策略

这一章的疑问很具体：代码主要由 AI 产出时，人靠什么保证结果不走样。

3.1 协作范式：人定边界，AI 填实现

本项目采用「意图驱动 + 强约束」的协作方式，人的职责集中在四件事，AI 负责在这些边界内产出实现：

人的职责具体做法在仓库中的痕迹
定边界先声明硬约束（零第三方依赖、Node ≥18、单文件前端、数据落 JSON），再让 AI 出方案prompts/01 第 2 节、README 技术栈表
定验收每个迭代先写「怎样算完成」，再写代码prompts/01 的 A/B/C/D 交付物表
做取舍对 AI 给出的备选方案逐条拍板，记录否决理由prompts/0x 的「方案取舍」表
复核不接受「看起来对」，必须给出状态码、日志或截图prompts/0x 的「验证记录」表

3.2 上下文管理

AI 走样的主要原因不是能力，而是上下文给错。本项目在每次迭代开场都会显式投喂三类信息：

  1. 硬约束：如「服务端必须零第三方依赖，不能引入 npm 包」。这条约束直接否决了 SQLite、Express、JWT 库等一整套方案，避免了后期回退。
  2. 现状事实：如「preview/index.html 的提交按钮目前只做了前端校验并跳转，订单从未落库」。用代码事实替代模糊描述，AI 才不会重复实现已有能力。
  3. 受影响文件：只喂需要改的文件与相邻的接口定义，避免把整个仓库塞进上下文导致风格漂移。
反例（真实发生）：在第一次建仓时，AI 用 PowerShell 把中文 JSON 作为命令行参数传给 curl，Windows PowerShell 5.1 按 GBK 编码传递参数，GitHub 收到非法 UTF-8 直接返回 400。定位后改为「UTF-8 文件 + --data-binary @file」一次通过。这类问题的正确处理方式是把失败现象与原始响应体一起回灌给 AI，而不是只说「报错了」。

3.3 Prompt 结构模板

凡是涉及多文件改动的任务，统一按下面的五段式组织，避免「帮我做个后台」这种开放式指令：

【角色】你是我这个零依赖 Node 项目的实现者，改动范围限定在 server/server.js 与 admin/index.html。
【约束】不引入任何第三方依赖；不改变现有接口的返回结构；错误统一 { code, message }。
【现状】后台目前没有任何鉴权，PUT /api/dishes/:id 可被匿名调用；前端靠隐藏按钮"假装"受限。
【目标】实现 Cookie 会话登录，受保护接口未登录返回 401，登录失败限速。
【验收】给出未登录 401、错误口令 401、正确登录 200、登出后 401 四组实测结果。

模板的价值在于把「验收标准」写进 Prompt 本身——AI 会主动围绕验收项组织实现，而不是堆功能。

3.4 五次迭代的 Prompt 链

仓库中 prompts/ 目录按迭代归档，每条记录都包含需求原文、AI 拆解、方案取舍、接口契约与验证记录。三次迭代的核心决策如下：

迭代关键决策被否决的方案与理由
01
订单落库		JSON 单文件存储；服务端重算金额；下单扣库存SQLite（node:sqlite 在 Node 18 不可用）；前端算价传后端（金额可篡改）；不扣库存（后台改库存成摆设）
02
登录鉴权		Cookie + 内存 Map 会话；口令 SHA-256 后定时安全比较；按 IP 限速JWT（零依赖下要自己实现 HMAC 与过期校验，收益低）；Basic Auth（无法主动登出）；全局失败计数（一人锁死所有人）
03
状态驱动跟踪		落 events 事件链；5 秒轮询；终态停止SSE / WebSocket（零依赖下握手与重连成本高，状态变化是低频事件）；用 updatedAt 推算时间轴（第二次改状态会覆盖第一次）
04
小程序端与双端架构		原生小程序 vs 跨端框架；TS strict；模块级状态；双端字段对齐uni-app / Taro（3 页规模下编译与调试成本高于收益）；购物车持久化（跨次启动带脏数据）
05
AI 推荐		本地营养学模型 + 组合搜索；大模型仅润色且默认关闭直接调大模型生成套餐（结果不可复现、无法解释、每次不同）；用模型改写数字（幻觉污染营养数据）

3.5 纠偏与复核

AI 的产出不直接进主干，必须过三道闸：

  1. 语法闸：node --check server.js 与内联脚本抽离后 node --check；
  2. 行为闸：用 curl 打真接口，核对状态码与响应体，覆盖正常路径 + 至少两条异常路径；
  3. 视觉闸：headless 浏览器截图，确认页面确实渲染成预期样子（防止「接口对但界面崩」）。

三道闸在 prompts/ 的验证记录表里逐条留痕，这也是第五章「可复现性论证」的证据来源。

3.6 约束清单

约束来源对实现的直接影响
零第三方依赖部署环境不可控，避免 npm install 失败路由、静态服务、Cookie 解析、原子写全部手写；代价是功能密度受限
Node ≥ 18评审可能用较老运行时不使用 node:sqlite 等新 API
前端单文件免构建、可直接双击查看/评审无打包工具、无框架，样式与逻辑内联

4.1 分层与职责

4.2 请求管线

request
  → 路由匹配（按 method + path 前缀，顺序敏感：精确匹配的 /api/orders 先于 /api/orders/:id）
  → 鉴权（仅受保护接口：PUT /api/dishes/*、POST /api/upload、GET /api/orders、PUT /api/orders/*）
  → 请求体读取（readBody 带体积上限：普通 64KB / 下单 256KB / 上传 8MB）
  → 参数校验（类型 + 范围 + 业务规则：菜品存在、单价 ≥ 基础价、库存充足）
  → 业务处理（重算金额 → 原子写菜单 → 原子写订单）
  → 统一响应（成功 { code:0, data }；失败 { code:, message }）

统一响应结构让前端可以用同一套 if (!res.ok || json.code !== 0) throw new Error(json.message) 处理所有接口，Toast 直接展示后端文案（如「「烟熏三文鱼沙拉」库存不足，仅剩 12 份」）。

4.3 数据一致性与原子写

JSON 文件最大的风险是「写一半崩溃 → 文件损坏 → 全部数据丢失」。本项目对所有持久化写入统一采用「临时文件 + rename」：

const writeOrders = (list) => {
  const tmp = ORDERS_FILE + '.tmp';
  fs.writeFileSync(tmp, JSON.stringify(list, null, 2), 'utf8');
  fs.renameSync(tmp, ORDERS_FILE);   // rename 在同一分区上是原子操作
};

下单时先写菜单（扣库存）再写订单，顺序不可颠倒：如果反过来，可能出现「订单已生成但库存没扣」的超卖；当前顺序最坏情况是「库存扣了但订单没落」，属于可接受的保守失败（少卖而非超卖），并已在限制说明中标注。

4.4 订单状态机

当前状态允许流转到触发方副作用
pending 待接单accepted / canceled商家追加事件；顾客端进度条推进
accepted 制作中done / canceled商家追加事件；顾客端显示「制作中」
done 已完成—（终态）商家追加事件；顾客端停止轮询
canceled 已取消—（终态）商家追加事件；顾客端隐藏进度条

服务端显式拒绝把状态改回 pending，其余非法值一律 400。事件链 events[] 与状态同步追加，保证时间轴永远可还原，而不是靠单一 updatedAt 猜测。

4.5 对生成代码的约束

约束落地方式
显式路由，不用中间件魔术每个接口一个 if (req.method === ... && url.startsWith(...)) 块，出错时能一眼定位
错误码约定400 参数 / 401 未登录 / 404 不存在 / 409 冲突（库存）/ 413 过大 / 429 限速 / 500 服务端
输入一律当敌人asInt(v,min,max) / asStr(v,max) 统一收口，禁止直接使用 req.body 字段
注释解释「为什么」如 // rename 在同一分区上是原子操作、// 首次运行时文件不存在
前端不重复业务逻辑前端算价仅用于展示；提交后以服务端返回的 total 为准

4.6 双端架构：小程序（生产）+ H5（展示）

同一个后端服务两个前端，是本项目对「可上架」与「可演示」这对矛盾的解法：

端目录职责与取舍

6　工程质量与安全

6.1 鉴权与会话

措施实现
会话载体服务端内存 Map<token, {user, expiresAt}>，令牌 crypto.randomBytes(24).toString('hex')
Cookie 属性HttpOnly（挡 XSS 读取）+ SameSite=Lax（挡跨站提交）+ Path=/ + Max-Age=28800
口令比对双方先 SHA-256 再 crypto.timingSafeEqual，避免长度与前缀的时序泄漏
暴力破解按 IP 计数，连续 5 次失败锁定 60 秒，返回 429 并给出剩余秒数
会话续期滑动续期：每次命中把过期时间推到 8 小时后

6.2 输入校验与金额可信

所有写接口遵循「先收口、再校验、后落库」：

const asInt = (v, min, max) =>
  typeof v === 'number' && Number.isInteger(v) && v >= min && v <= max ? v : null;
const asStr = (v, max) => (typeof v === 'string' ? v.trim().slice(0, max) : '');

支付相关字段（unitPrice、qty）只被当作「输入」而非「结果」：小计、配送费、打包费、合计、总热量全部由服务端基于菜单与计费规则重算；unitPrice 仅允许 ≥ 菜品基础价（规格只能加价）。

6.3 并发与文件一致性

当前写入路径是 read → 改 → write，多请求并发下单存在竞态窗口（两个请求可能读到同一份库存）。单机演示场景可接受，已在限制中标注；后续方案是文件锁（fs.open + 独占标志）或迁移 SQLite 事务。
