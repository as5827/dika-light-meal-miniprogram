# 对话快照 02 · 推荐引擎：从"能算出一套"到"算得站得住"

> **第 2 条完整 Prompt 链。** 四段结构：**① 我提的 Prompt（原文）→ ② AI 给出的第一版方案 →
> ③ 我怎么引导它纠偏（三轮调参）→ ④ 验收结果。**
>
> Prompt 为当时原文引用；AI 回复保留关键段落，数字与日志是当时跑出来的真值。

## ① 我提的 Prompt

> 本项目为减脂餐创业商家打造轻量化点餐小程序……业务层面：面向小微轻食商家，提供低成本数字化接单方案，
> **内置 AI 个性化减脂套餐推荐，结合用户身体指标给出适配餐品**，同时双前端架构兼顾真实业务落地与评审演示便捷性。

## ② AI 给出的第一版方案

用大模型直接生成套餐，理由是"这样更像 AI"。

**我否掉了。** 三条理由写在 `prompts/05` 里：结果不可复现、评审问"为什么是这三道菜"答不上来、每次调用都要钱要网要 key。
改成**本地营养学模型 + 组合搜索**，大模型只负责把结论说顺口。

## ③ 我怎么引导它纠偏（三轮）

### 第一轮：蛋白量失控

第一版跑出来是这样（女 28 / 165cm / 58kg / 轻度活动 / 减脂）：

```
目标：每日 1441 kcal、蛋白 93 g；单餐预算 576 kcal / 37 g
推荐：鸡胸肉藜麦沙拉 + 额外鸡胸肉 + 番茄时蔬汤
合计：600 kcal、蛋白 64 g   蛋白达成 173%
```

热量贴合，蛋白顶到目标的 1.7 倍。**这不是"个性化"，是把所有能加蛋白的东西堆上去。**

我的追问：「蛋白达成 173% 明显不合理，你看下目标函数是不是没有上限」。

目标函数原本是：

```
score = 蛋白达成×0.5 − 热量偏差×0.35 + 价格分×0.15
```

蛋白项被 `min(1.6, p/target)` 截断在 1.6，等于告诉算法"蛋白越多越好"。加上过量惩罚：

```
overProtein = max(0, 蛋白 − 目标×1.3) / 目标
score = … − overProtein × 0.2
```

再跑：

```
合计 530 kcal、蛋白 59 g（目标 37 g，达成 159%）
```

仍然偏高，但这是有意的：轻食客群本来就冲高蛋白来的，压到 90% 反而会推荐出"蔬菜沙拉 + 气泡水"这种没价值的组合。**这个度是人工定的，不是算法自己选的。**

### 第二轮：预算太狠

我的追问：「预算填 10 块，接口返回无解，这个体验不行，得有退化方案」。

改成两段式：

1. 先在预算内搜索；
2. 无解时退化为「满足营养下限（蛋白 ≥60%、热量 ≥70%）的最便宜组合」，并在结果里标 `budgetRelaxed: true`。

返回 ¥26 的全麦鸡胸三明治，前端明确写"预算内没有合适组合，已自动放宽"。

### 第三轮：营养数据从哪来

第一版想接公开营养库，但 28 道菜要逐条映射、还要处理"同菜不同做法"，成本和误差都不可控。

我的决定是**宁可承认是估算**：每道菜补一个 `protein` 估算值，`data/menu.json` 里写明
`nutritionNote: "protein 为估算值（g），仅用于推荐算法演示，非实验室检测数据"`，文档里也标了。

## ④ 验收结果

| 用例 | 结果 |
|---|---|
| 手算核对（女 28/165/58/轻度） | BMR 1310、TDEE 1801，与公式手算一致 |
| 素食过滤 | 三项全部素食 |
| 预算 ¥10 | 放宽后给最便宜合规组合，并标注 |
| 同参数两次请求 | 菜品 id 完全一致 |
| 非法参数 | 400 + 中文提示 |
| 候选规模 | 674 个组合，引擎耗时 2–6 ms |

## 复盘

"AI 推荐"最容易糊弄的地方是：随便给一套，说这是模型算的。要让它站得住，得能回答三个问题——**输入是什么、怎么算的、为什么是这个结果**。所以推荐日志里把候选数、耗时、选中菜品、偏差全打出来了，界面上也把每一步的中间结论直接摊开给人看。
