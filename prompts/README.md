# prompts/ · AI 协作过程归档

本目录留存本项目「人类意图 → AI 协作 → 代码落地」的完整链路，用于满足赛项对**过程可复现性（25%）**的核查：

> 须包含至少 3 个核心功能迭代时与 AI 交互的完整 Prompt 链（Prompt 提问、AI 的修改建议、如何引导 AI 修复 Bug）。

## 归档约定

| 约定 | 说明 |
|---|---|
| 一次核心功能迭代 = 一个 `.md` 文件 | 文件名 `NN-功能名.md`，编号与提交顺序一致 |
| 一次迭代对应一次（或多次）语义化 commit | commit message 中标注对应的 prompt 文件编号 |
| 只记录真实发生的交互 | 不做事后补写、不编造对话 |
| 敏感信息脱敏 | 任何 token / 密钥 / 手机号在归档前打码 |

## 单个文件的最小结构

1. **原始需求**：人类输入的原文（不改写）
2. **上下文**：当时的代码状态、约束条件
3. **AI 拆解与方案**：需求被拆成哪些可交付项，为什么这样拆
4. **方案取舍**：备选方案与放弃理由（这是评审最容易看出"是否真在思考"的部分）
5. **关键 Prompt 与产出**：可复用的 Prompt 片段、AI 给出的关键代码/结论
6. **验证记录**：怎么证明它真的跑通了（命令、状态码、截图位置）
7. **遗留问题**：这次没做什么，为什么

## 关于本机制建立之前的历史

仓库最早的 6 次提交是**存量代码按模块导入**（README / 服务端 / 数据 / 点餐页 / 后台 / 换行规范），早于本归档机制建立，因此没有对应的 Prompt 记录。

这一点在 `README.md`「比赛提交对照」中已如实标注，不做追溯性补写——伪造的 Prompt 链在评审追问下必然崩塌，不如把可信度押在真实的后续迭代上。
