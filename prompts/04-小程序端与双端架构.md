## 1. 原始需求

> 我想要做的是可以上架微信小程序端的 做 web 版本是为了方便在网页端查看 所以就是相当于做了两套代码 一套代码是实际应用的一套是方便展示的 你根据我的意思补充完善一下这个项目代码

随消息附了一张技术栈截图，期望：微信原生小程序（不用 uni-app / Taro / mpvue）、TypeScript strict、WXML + WXSS、运行时零依赖。

这句话其实是一次**定位纠正**：此前我把 H5 当成了主体、小程序当成"以后再补"，而真实的产品意图是反过来——**小程序是交付物，H5 只是演示壳**。

## 2. AI 的拆解

- **重新划分两层**：`miniprogram/`（生产端，上架用）+ `preview/`、`admin/`（展示与运营），`server/` 两端共用；
- **小程序端做一个完整闭环**，不做半成品：点餐（含规格弹层）→ 确认订单（地址/费用/备注）→ 订单跟踪（状态 + 事件时间轴）；
- **字段与 Web 端严格对齐**，让"同一套接口"不是口号：规格加价用 `deltaPrice`、计费规则取 `menu.fees`、金额以「分」传输；
- **把"能不能上架"拆成代码条件与资质条件**，后者写进 README 与文档，不假装技术能解决一切。

## 3. 方案取舍

| 决策点 | 备选 | 选择与理由 |
|---|---|---|
| 跨端框架 | uni-app / Taro / 原生 | **原生**。只有 3 个页面，框架的编译产物、调试链路与版本兼容成本都高于收益；且本项目要的是"微信里真的能用"，不是"多端发布" |
| 语言 | JS / TypeScript strict | **TS strict**。在没有运行时测试的前提下，类型是唯一能在提交前挡下 `deltaPrice` 写成 `delta` 这类错误的闸门；开发者工具原生编译 TS，不需要额外构建 |
| 状态管理 | mobx-miniprogram / 模块级单例 | **模块级单例**。状态只有「一车商品」，observable 那套反而增加心智负担；页面 `onShow` 主动 `syncCart()` |
| 规格默认值 | 空选 → 禁用按钮 / 默认选中每组第一项 | **默认选中**。必选组永远有值，用户不必先点一遍才能看到价格 |
| 购物车持久化 | 存 Storage / 不存 | **不存**。跨次启动带着上次没下单的商品，比"丢了再选"更糟 |
| 收货地址 | 不存 / Storage | **存**。地址几乎不变，重复填写是主要摩擦点 |
| 状态同步 | WebSocket / SSE / 轮询 | **5 秒轮询**，与 H5 保持一致；订单状态是低频事件，两端逻辑相同便于讲清楚 |

## 4. 接口与字段对齐核对

| 环节 | 字段 | 核对结果 |
|---|---|---|
| 菜单 | `dishes[].specs[].options[].deltaPrice` | ✅ 从 `data/menu.json` 实际读取得知（不是文档里写的 `delta`） |
| 计费 | `fees.deliveryFee / packFee / freeDeliveryThreshold` | ✅ 三字段齐全，页面按 `subtotal >= freeDeliveryThreshold` 判免配送 |
| 下单 | `POST /api/orders { items[{dishId,qty,unitPrice,specDesc}], address{name,phone,building,room}, remark }` | ✅ 与服务端校验一致；`unitPrice = 基础价 + Σdelta`，满足「单价 ≥ 基础价」 |
| 查询 | `GET /api/orders/:id → { status, events[], total, itemCount, address.phone(脱敏) }` | ✅ 跟踪页用 `events` 渲染时间轴 |

> 这次核对发现一个真实问题：**README 的规格示例写的是 `"delta": 0`，而数据里是 `deltaPrice`**。小程序端写完后回头把 README 示例一并改正——这类"文档与数据打架"的坑，正是双端对齐时最容易漏掉的。

## 6. 遗留问题（诚实声明）

- **本机没有微信开发者工具**，UI 未经模拟器/真机验证，只做了 TypeScript 静态检查与接口契约核对——这一条必须写清楚，不能把"编译通过"说成"跑通了"；
- 未接 `wx.login`：顾客仍以订单号为凭证，订单不归属到具体用户；
- 未接微信支付：当前是线下/到店结算；
- 购物车未持久化（刻意为之，见取舍表）；
- 未做分享卡片、订阅消息、骨架屏等小程序侧体验细节。

## 7. 上架前置条件（代码之外）

HTTPS 域名 → ICP 备案 → 服务器域名白名单 → 餐饮类目资质（食品经营许可证）→ 隐私保护指引配置。这五项不解决，代码再干净也提交不了审核。
