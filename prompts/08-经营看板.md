# 08 · 经营看板

- **日期**：2026-10-29
- **对应提交**：`feat(stats): 经营看板`、`docs: 看板章节与材料同步`
- **上游问题**：赛道推荐方向 6 的描述是「基于标准数据格式的智能分析系统 + 动态图表大盘 + 大模型对长尾数据做趣味解读」。原项目只有商品与订单管理，没有"看数据"这一面，对位是虚的。

---

## 1. 需求

商家想知道今天卖得怎么样：几单、多少钱、什么卖得好、什么时候忙、顾客点的热量高不高。原来这些只能一条条翻订单。

## 2. 拆解

| 交付 | 验收 |
|---|---|
| 聚合接口 | 今日订单数（含待接/完成/取消）、营业额、客单价、24 小时分布、热销 Top5、客单热量分桶、库存告急 |
| 看板界面 | 后台一个区块，指标卡 + 时段柱状 + 热销条 + 热量分布条 |
| AI 解读 | 一键让模型读今天的数字，给 3 条建议；没有 Key 时用模板 |
| 数字可信 | 模型只能复述给定的数字，不新增、不推测 |

## 3. 取舍

| 决策点 | 备选 | 选择与理由 |
|---|---|---|
| 图表库 | 引 ECharts / 手写 canvas / 纯 CSS 条 | **纯 CSS 条**。项目零依赖是卖点，为几张图引一个 300KB 的库不值；这里的数据量级也不需要交互图表 |
| 统计口径 | 全部订单 / 排除已取消 | **排除已取消**。取消单不该进营业额与客单价，否则数据虚高 |
| 热量统计 | 按单品累加 / 按订单合计后分桶 | **按订单合计分桶**。顾客关心的是"这一餐多少卡"，不是单个菜 |
| AI 角色 | 让模型自己算 / 数字算好只让它解读 | **只解读**。模型不会数数，让它算必然出错；把结构化数字喂给它，只要求写建议 |
| 无 Key 时 | 报错 / 隐藏入口 / 模板文案 | **模板文案**。模板用同一份数字拼句子，逻辑与模型版一致，只是不好听 |

## 4. 接口

```http
GET  /api/stats            （需登录）
POST /api/stats/insight    （需登录）
```

`GET /api/stats` 返回今日聚合：`orders{total,active,done,pending,canceled}`、`revenue`、`avgTicket`、
`hours[24]`、`topDishes[5]`、`calorie{avg,buckets[4]}`、`inventory{low,soldOut}`、`peakHour`。

`POST /api/stats/insight` 返回 `{ text, source }`，`source` 为 `llm` 或 `template`。

## 5. 验证

用 7 笔测试订单（含 1 笔库存不足被 409 拒绝）跑通：

| 检查 | 结果 |
|---|---|
| 聚合准确性 | 6 单、营业额 ¥418、客单价 ¥70、峰值 19 点，与手工核算一致 |
| 热销排序 | 鸡胸肉藜麦沙拉×4、烟熏三文鱼沙拉×3、照烧鸡腿糙米碗×2… |
| 热量分桶 | 300–500 两单、>700 四单，与订单热量对得上 |
| AI 解读 | `source=llm`，输出 3 条建议，数字全部来自接口（6 单、售罄 4 项、19 点、¥70） |
| 未配 Key | `source=template`，输出同结构的一句话摘要 |
| 权限 | 未登录访问 `/api/stats` 返回 401 |

## 6. 没做的

- 没做多日趋势与同比（需要更长时间的数据积累，两天造不出来）；
- 没做导出 CSV / Excel；
- 图表固定为"今日 + 8–22 点"，没有做时间范围切换；
- 模型解读没有做缓存，同一份数据重复点会重复计费。
