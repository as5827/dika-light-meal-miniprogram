实际卡住的四个环节

① 建仓接口 400

POST /user/repos → 400
{"message":"Problems parsing JSON"}

原因：PowerShell 5.1 把中文描述按 GBK 编码传给 curl.exe，GitHub 收到非法 UTF-8。

改法：把 JSON 写进 UTF-8 文件，用 --data-binary @file。一次通过，返回 201。

② "Repository not found" 不是权限问题

git ls-remote 报 not found，第一反应是权限，实际是仓库根本没创建成功（上一条的 400 就是根因）。

③ 换账号时撞上风控

ssh -T git@github.com      → Hi grorge00! You've successfully authenticated
GET /users/grorge00        → 404
GET /users/grorge00/repos  → 200 []

SSH 能认证、公开资料却 404，说明账号在库里存在但未公开（新号被标记）。这种号即使推上去，评委点链接也是 404。决定换号，改成 as5827（同一台机器上有它的凭据）。

④ push 反复被重置

fatal: unable to access 'https://github.com/...': Recv failure: Connection was reset

排查顺序：先怀疑仓库权限（不是）→ 再查连通性（api.github.com 通、github.com 超时）→ 最后发现系统里开着代理 127.0.0.1:7897，但 git 完全没走它。

git config http.proxy http://127.0.0.1:7897
git push → 成功

我做的三个决定

决定依据
不追 grorge00，直接用 as5827新号 404 意味着评委打不开，比赛场景下不能赌
不把 token 写进仓库或配置只从系统凭据里读，用完即走；后来改成 Cookie 会话 + 环境变量
本地目录先迁到 Desktop 管理的新位置，再删旧的两份代码必然改错，只留一份

结果

  • 提交历史完整上线（先 6 条，后续迭代到 27 条）；
  • 推送通道固定为「代理 + 系统凭据」，git push 不再需要额外参数；
  • GitHub Desktop 接管本地目录，与远程保持同步。

复盘

这次折腾的教训不是"命令记错了"，而是结论下得太早：把"我这边 push 成功"当成了"评委能打开"。后面所有验收都改成用匿名接口复核（private:false、能否匿名读 README），而不是只看命令行回显。

对话快照 02 · 推荐引擎：从"能算出一套"到"算得站得住"

说明：对话纪要（节选）。这里的取舍不是一次成型，中间被推翻过一轮。

我说的（原话）

本项目为减脂餐创业商家打造轻量化点餐小程序……业务层面：面向小微轻食商家，提供低成本数字化接单方案，内置 AI 个性化减脂套餐推荐，结合用户身体指标给出适配餐品，同时双前端架构兼顾真实业务落地与评审演示便捷性。

它先给的方案

用大模型直接生成套餐，理由是这样"更像 AI"。

我否掉的原因写在 prompts/03 里：结果不可复现，评审问"为什么是这三道菜"时答不上来；而且每次调用都要钱、要网、要 key。改成本地营养学模型 + 组合搜索，大模型只负责把结论说顺口。

第一版跑出来的问题

女 28 岁 / 165cm / 58kg / 轻度活动 / 减脂：

目标：每日 1441 kcal、蛋白 93 g；单餐预算 576 kcal / 37 g
推荐：鸡胸肉藜麦沙拉 + 额外鸡胸肉 + 番茄时蔬汤
合计：600 kcal、蛋白 64 g
蛋白达成 173%

热量贴合，蛋白直接顶到目标的 1.7 倍。这不是"个性化"，是把所有能加蛋白的东西堆上去。

怎么改的

目标函数原本是：

score = 蛋白达成×0.5 − 热量偏差×0.35 + 价格分×0.15

蛋白项被 min(1.6, p/target) 截断在 1.6，等于告诉算法"蛋白越多越好"。加了过量惩罚：

overProtein = max(0, 蛋白 − 目标×1.3) / 目标
score = … − overProtein × 0.2

再跑：

合计 530 kcal、蛋白 59 g（目标 37 g，达成 159%）

仍然偏高，但这是有意的：轻食客群本来就冲高蛋白来的，压到 90% 反而推荐出"蔬菜沙拉 + 气泡水"这种没价值的组合。这个度是人工定的，不是算法自己选的。

第二轮问题：预算太狠

预算填 ¥10，第一版直接返回"无解"。改成两段式：

  1. 先在预算内搜索；
  2. 无解时退化为「满足营养下限（蛋白 ≥60%、热量 ≥70%）的最便宜组合」，并在结果里标 budgetRelaxed: true。

返回 ¥26 的全麦鸡胸三明治，前端明确写"预算内没有合适组合，已自动放宽"。

第三轮问题：营养数据从哪来

第一版想接公开营养库，但 28 道菜要逐条映射、还要处理"同菜不同做法"，成本和误差都不可控。最后：

  • 每道菜补一个 protein 估算值；
  • 在 data/menu.json 里写明 nutritionNote: "protein 为估算值（g），仅用于推荐算法演示，非实验室检测数据"；
  • 文档里也标了。

宁可承认是估算，也不把假数据包装成检测报告。

对话快照 03 · 让大模型只改语气，别动数字

说明：对话纪要（节选）。包含一次真实调用、一次兜底测试，以及"去 AI 味"的具体改法。

我说的（原话）

API key:sk-\*\*\*\*（已脱敏） 调用一下试试并且再编辑润色文档和日志 尽量去除ai痕迹

两个要求：真的打通大模型，文档别写成一嘴 AI 腔。

第一步：先确认 key 能用

先不接业务，直接打 POST /v1/chat/completions：

HTTP 200 · model: deepseek-flash
choices[0].message.content: 减脂期保证蛋白质摄入，是因为……

第二步：约束它别乱动数字

推荐结果里全是算出来的数（BMR、目标热量、蛋白克数、偏差百分比），模型一旦"顺手改写"，前面的算法就白算了。系统提示直接写死：

你是一位耐心、鼓励型的营养师。你只能改写语气，不得修改、新增、删除任何数字或结论；
输出 120 字以内中文，不要分点。

同一份数据，两次输出对比：

模板：……这套组合合计 590 kcal、蛋白 55 g，热量偏差 +2%，蛋白达成 153%。
润色：……你这套组合合计 590 kcal、蛋白 55 g，热量只偏差 +2%，蛋白达成 153%，挺不错的，继续加油！

逐位比对：1312 / 1804 / 1443 / 91 / 40% / 577 / 36 / 590 / 55 / +2% / 153% —— 11 个数字全部一致。

第三步：不确定的情况要能兜底

把 key 换成一个无效值再请求：

code=0，aiReason 为空，reason 仍是模板文案，耗时 0.3s

接口不报错、页面不缺内容，只是少了那句"继续加油"。这一点写进了 prompts/05 和 README 的限制表：大模型是增强项，不是依赖项。

第四步：去 AI 味

这一条比接 key 麻烦。改了三类东西：

原来改成为什么
本章回答一个问题：在「代码主要由 AI 产出」的前提下……这一章的疑问很具体：代码主要由 AI 产出时，人靠什么保证结果不走样。设问句 + 长定语是典型的模型腔
几个刻意的设计：蛋白过量要扣分……几处取舍：蛋白质超过目标 1.3 倍开始扣分……"刻意的设计"是在自我表扬，读着假
诚实声明： ……伪造的 Prompt 链在评审追问下必然崩塌说明： 最早的 6 次提交早于归档机制，这里也不补写。解释"我为什么诚实"本身就是表演

另外把 prompts/*.md 的标题统一成「需求 / 拆解 / 取舍 / 接口 / 验证 / 没做的」，去掉「AI 的拆解」「协作形态：DSH Agent 会话」这类标签——标签是给机器看的，记录是给人看的。

复盘

"让 AI 写得像人"最容易走偏的地方，是把它改得更花哨。实际有效的只有三件事：去掉自我评价、去掉设问和排比、把每句话落到具体数字和具体动作上。第三点尤其重要——"处理了并发问题"是空话，"先写菜单再写订单，最坏是少卖而不是超卖"才是人写的。

3. 取舍

决策点备选选择与理由
存储SQLite（node:sqlite）/ 单文件 JSON / 内存单文件 JSON。零依赖约束下最稳；node:sqlite 在 Node 18 不可用，而 README 承诺 Node ≥ 18；内存方案重启即丢，无法体现"落库"
写入方式直接 writeFileSync / 临时文件 + rename沿用现有 writeMenu 的原子写。JSON 被写坏 = 全部订单丢失，这个风险不值得省几行代码
金额计算前端算好传给后端 / 后端重算后端重算。前端传 unitPrice 只作为规格加价后的单价依据，小计、配送费、打包费、合计、总热量全部服务端重算——这是"金额不可被前端篡改"的最小防线
库存不扣 / 下单扣减下单扣减。否则后台改库存只是摆设，闭环不成立；库存不足直接 409 拒绝下单
订单状态只存 pending / 四态流转四态（待接单 / 制作中 / 已完成 / 已取消），否则后台没有可操作的东西
订单文件入库提交 data/orders.json / 忽略忽略。提交一个空 JSON 会让每次本地测试产生脏 diff；改为提供 data/orders.example.json 说明结构，运行时自动创建

6. 没做的

  • 订单文件容量：当前只做「保留最近 N 条」的截断，未做分页与归档；

2. 拆解

一句话：把「后台」这个角色显式建模出来，而不是靠前端藏按钮。

  • 服务端：会话签发 / 校验 / 失效 + 受保护接口清单 + 登录失败限速；
  • 后台页：启动先探测会话，未登录弹登录遮罩；接口返回 401 时统一回到登录态；
  • 顾客端：不受影响（下单、查自己的订单仍需匿名可用）。

3. 取舍

决策点备选选择与理由
会话载体JWT / HttpOnly Cookie + 服务端 Map / Basic AuthCookie + 内存 Map。零依赖下 JWT 要自己实现 HMAC 与过期校验，收益不大；Basic Auth 每次请求带密码，浏览器体验差且无法主动登出；内存 Map 重启即失效，正好符合「演示态」定位，代价写进限制说明
Cookie 属性普通 Cookie / HttpOnly + SameSiteHttpOnly + SameSite=Lax + Path=/。HttpOnly 挡 XSS 偷 token，SameSite 挡跨站请求伪造；不过 HTTPS 环境下还应加 Secure，本地 http 调试加不了，已记入遗留
口令比对=== / 哈希后 timingSafeEqual哈希后定时安全比较。原始字符串比较会因长度/前缀提前返回而泄漏时序信息，timingSafeEqual 要求等长，所以先各自 SHA-256
会话续期固定过期 / 滑动续期滑动续期（每次命中延长到 8 小时）。演示时不会写着写着被踢出去
暴力破解不限 / 全局计数 / 按 IP 计数按 IP 计数，5 次失败锁 60 秒。全局计数会被一个人锁死所有人
默认口令硬编码 / 环境变量环境变量优先，缺省 admin/dika2026。缺省值写进启动日志与登录框提示，保证评委 git clone 后零配置可复现
顾客端订单查询也要登录 / 凭订单号匿名查凭订单号匿名查，且 手机号脱敏（136****5678）。订单号即凭证，评委无需账号也能看到跟踪闭环

4. 计算链路

身体指标 → Mifflin-St Jeor
  BMR = 10×体重 + 6.25×身高 − 5×年龄 + (男 5 / 女 −161)
→ TDEE = BMR × 活动系数(1.2 / 1.375 / 1.55 / 1.725)
→ 每日目标 = TDEE × 目标系数(减脂 0.8 / 维持 1.0 / 增肌 1.1)，并设下限 1200/1400/1600
→ 蛋白目标 = 体重 × (1.6 / 1.2 / 1.8) g
→ 单餐预算 = 目标 × 40%
→ 组合搜索：主菜(1) × 加料(0-1) × 汤/果汁(0-1) × 甜点(0-1)，约 1.5k 组合
→ 目标函数打分，取最高

  • 对应提交：feat(nl): 自然语言点餐 → docs: 文档与材料同步
  • 上游问题：赛道的 10 个推荐方向里没有餐饮，作品容易被看成"普通点餐系统"；推荐模块又被定位成"AI 只润色"，AI 含量不足以支撑 20% 的「方法创新性与意图控制」

1. 需求

你全部都做然后上传 GitHub —— 让这个项目从"点餐系统 + 一个小推荐"变成"能听懂人话的点餐助手"

本来的交互是：用户翻类目、看菜品、自己算热量。改成：说一句话，系统把话拆成条件，再筛。

2. 拆解

交付验收
意图解析接口一句话 → 结构化条件；模型失败时正则兜底
条件筛选热量/蛋白/价格/素食/忌口/关键词，六个维度都能生效
筛不到时放宽逐级去掉最软的条件，并把"放宽了什么"回传
双端入口H5 菜单页顶部输入条；小程序同款
可复现同一句话 + 同一菜单 = 同一结果，temperature=0 且筛选在本地

3. 取舍

决策点备选选择与理由
谁来解析让模型直接推荐菜品 / 模型只解析条件只解析。让模型点菜，它每次给你的组合都可能不同，评审问"为什么是这三道"就答不上；解析成条件后，筛选在本地跑，结果可复算
解析失败直接报错 / 猜一个默认条件 / 正则兜底正则兜底。"500千卡以内""不要香菜""预算40"这些说法用正则就能覆盖大半，配置没到位或网络抖动时也不至于功能不可用
模型输出校验信任模型返回 / 逐字段校验逐字段校验：数值做范围截断，数组限制长度与条数，非法值直接丢弃，不做猜测
筛不到怎么办返回空 / 自动放宽 / 自动推荐别的逐级放宽并回传。关键词 → 忌口 → 蛋白 → 价格 → 热量 → 素食，每去掉一项就记一笔，前端明说"已放宽 xxx"，不假装命中
条件怎么展示只给结果 / 结果 + 条件标签标签化。用户能一眼看出模型理解对不对（比如把"高蛋白"理解成没条件），这是意图对齐最便宜的验证方式
双端一致性只做 H5两端都做。小程序是生产端，H5 是演示端，功能缺一个都说不通

4. 接口

POST /api/nl-order
{ "text": "我想吃500千卡以内、高蛋白、不要香菜，预算40" }

→ 200
{
  "source": "llm",              // llm | llm+fallback | fallback | none
  "conditions": { "maxCalorie": 500, "maxPrice": 40, "excludeKeywords": ["香菜"], ... },
  "tags": ["热量 ≤ 500 kcal", "价格 ≤ ¥40", "不要香菜"],
  "dropped": [],                // 被放宽掉的条件
  "dishes": [ { "id": "d13", "name": "香煎鸡胸配时蔬", "calorie": 330, "protein": 33, ... } ]
}

5. 验证

用例结果
"500 千卡以内、高蛋白、不要香菜，预算 40"source=llm，条件解析为热量 ≤500 / 价格 ≤40 / 不要香菜，命中 8 道，前三是香煎鸡胸(330kcal/33g)、鸡胸藜麦沙拉(320/32)、清蒸龙利鱼(260/28)
"来点素的，热量别超过 300"只筛选素食，命中 7 道，首位抹茶豆腐慕斯 190kcal
"想吃鸡胸，蛋白 25 克以上"命中 3 道，蛋白全部 ≥25g
"预算 30，来碗热的"关键词"热"无匹配 → 自动放宽，dropped=["想吃热"]，返回价格 ≤30 的 8 道
未配置 Key 时的同一句话source=fallback，正则解析出热量/价格/忌口，结果与模型版接近
小程序端 tsc --noEmit0 error

6. 没做的

  • 不做多轮追问（"再来点清淡的"这类依赖上下文的说法，当前每次独立解析）；
  • 不做方言与错别字纠正，正则兜底只覆盖常见句式；
  • 模型解析结果没有做缓存，同一句话重复请求会重复计费；
  • 没接菜单之外的知识（比如"适合增肌的"这种需要营养学推理的说法，只能落到关键词）。
