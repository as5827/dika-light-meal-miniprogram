# 1 项目概述

## 1.1 背景

校园周边的小微轻食外卖店，日常经营高度依赖微信群：每天在群里发菜单、顾客接龙下单、店主人工汇总。这类门店单量不大（二十单上下），既没有预算上一套 SaaS，也没有必要。本作品面向这一场景，提供一套可自托管、跑起来不需要装依赖的点餐系统，并把「AI 定制减脂套餐」和「一句话点餐」两个 AI 能力做进点餐流程里。

## 1.2 问题描述

现有做法有三个具体摩擦：

- **菜单版本散落。** 改一次价就要重新发一遍群消息，历史消息刷走后顾客找不到当前价格。
- **库存靠口头确认。** 「还有吗」要一条条回，重复接单和「卖完了忘了说」同时存在。
- **进度不透明。** 下单后顾客反复问「好了没」，而店主一人同时接单与出餐，答不过来。

## 1.3 建设目标

| 目标 | 验收口径 |
|---|---|
| 菜单单一数据源 | 后台改价即时生效，顾客端无需刷新缓存 |
| 下单前完成校验 | 估清菜品售罄置灰，金额由服务端重算 |
| 订单状态可见 | 顾客凭订单号查询，状态由服务端事件链驱动 |
| 经营数据可读 | 订单聚合成一屏看板，含热销与热量分布 |
| AI 能力可用且可解释 | 推荐结果给出组合、偏差与理由；模型不参与计算 |
| 点餐有记忆 | 同一顾客再次进入时，能看到基于历史订单的复盘与建议 |

## 1.4 术语与缩写

| 术语 | 说明 |
|---|---|
| SKU | 规格组合单位，同一菜品的不同份量或加料视为不同 SKU |
| 估清 | 当日备货售罄，菜品置灰且不可下单 |
| BMR / TDEE | 基础代谢率 / 每日总能量消耗，单位 kcal |
| 意图驱动开发 | 人定约束与验收，AI 在边界内产出实现 |
| SSE | Server-Sent Events，服务端向浏览器单向推送事件流 |

# 2 需求分析

## 2.1 用户角色

| 角色 | 使用场景 | 关键诉求 |
|---|---|---|
| 顾客 | 手机浏览器或小程序点餐 | 看得清价格与库存、下单快、知道做到哪了 |
| 商家 | 电脑或平板打开后台 | 改菜单、接单、看当天经营情况 |

## 2.2 功能需求

| 模块 | 功能 | 级别 |
|---|---|---|
| 菜单浏览 | 8 个类目、28 道菜品，分类与列表滚动双向联动，售罄置灰 | P0 |
| 规格与购物车 | 多规格组、加价联动、本地持久化 | P0 |
| 下单 | 服务端重算金额、校验库存、幂等下单 | P0 |
| 订单跟踪 | 状态事件链 + 轮询刷新，终态停止 | P0 |
| 商家后台 | 登录、菜品编辑、接单与状态流转 | P0 |
| AI 套餐推荐 | 按身体指标计算单餐目标，组合搜索给出套餐 | P1 |
| 一句话点餐 | 自然语言转结构化条件并筛选 | P1 |
| 经营看板 | 订单聚合成指标与图表，附解读 | P1 |
| AI 响应可视化 | 推荐与点餐的处理阶段实时呈现 | P1 |
| 点餐搭档 | 按订单记忆口味与营养，主动给建议并一键加购 | P1 |

## 2.3 非功能需求

- **零第三方运行时依赖**：根目录无 `package.json`，`node server/server.js` 即可启动，避免评审机装不上依赖。
- **单机可跑**：数据落 JSON 文件，不依赖数据库服务。
- **降级可用**：大模型不可用时退回模板文案与规则解析，功能不中断。
- **可复现**：构建、运行、文档生成均有确定命令，不依赖个人环境。

## 2.4 范围界定

| 维度 | 本期做 | 本期不做（原因） |
|---|---|---|
| 交易 | 下单、金额重算、库存扣减、状态流转 | 支付与退款：需要商户资质与回调联调，个人赛周期内无法真实验证 |
| 履约 | 商家接单与完成，顾客端可见 | 骑手调度：本项目不涉及真实配送体系，不虚构骑手信息 |
| 账号 | 商家单账号 Cookie 会话 | 顾客注册：以订单号作为查询凭证，降低使用门槛 |

# 3 系统设计

## 3.1 总体架构

一套后端、两个前端。三者共用同一套 REST 接口，业务逻辑只实现一次。

```
顾客端（H5 / 小程序）        商家后台（H5）
        └──────────┬──────────────┘
             /api/* REST 接口
                   │
        Node 原生 HTTP 服务（零依赖）
        ├─ 路由分发与静态托管
        ├─ 会话鉴权（Cookie）
        ├─ 业务模块 recommender / intent / stats
        └─ 原子读写 → data/menu.json、data/orders.json
```

## 3.2 模块划分

| 模块 | 职责 | 规模 |
|---|---|---|
| `server/server.js` | 路由分发、静态托管、会话鉴权、参数校验、原子写、订单状态机 | 约 950 行 |
| `server/recommender.js` | 营养学模型与组合搜索 | 约 260 行 |
| `server/intent.js` | 自然语言转条件、逐级放宽筛选 | 约 230 行 |
| `server/stats.js` | 订单聚合与模板解读 | 约 150 行 |
| `server/logger.js` | 结构化日志与脱敏 | 约 100 行 |
| `preview/` | 顾客端 H5：菜单、规格、购物车、结算、跟踪 | 单文件 |
| `admin/` | 商家后台：登录、菜品编辑、订单列表 | 单文件 |
| `miniprogram/` | 微信原生小程序（TypeScript strict） | 三页 + 服务层 |

## 3.3 技术选型

| 决策 | 备选 | 选择理由 |
|---|---|---|
| Node 原生 `http` | Express / Koa / NestJS | 需求只有十几个接口，框架带来的依赖与升级成本大于收益 |
| JSON 文件原子写 | SQLite / MySQL | `node:sqlite` 在 Node 18 不可用；文件足够，且便于评审直接查看数据结构 |
| 原生小程序 | uni-app / Taro / React Native | 3 页规模下，跨端编译链路的调试成本高于收益 |
| 前端单文件、无构建 | Vite / Webpack | 免构建才能「双击即可查看」，评审不必装工具链 |
| 金额以「分」为整数 | 浮点元 | 浮点误差不可接受，展示层统一转换 |

## 3.4 数据模型

| 实体 | 主要字段 | 说明 |
|---|---|---|
| 菜品 `dish` | `id`、`name`、`price`（分）、`calorie`、`protein`、`stock`、`tags`、`specGroups` | `protein` 为估算值，界面已标注 |
| 订单 `order` | `id`、`status`、`items`、`total`、`fees`、`address`、`events` | `events` 为状态事件链 |
| 会话 `session` | `token`、`user`、`expiresAt` | 内存 Map，进程重启失效 |
| 菜单 `menu` | `categories`、`dishes`、`fees`、`nutritionNote` | 唯一数据源，前后端共用 |

订单状态流转：`pending`（待接单）→ `accepted`（已接单）→ `done`（已完成）；`pending` / `accepted` 可转 `canceled`。

## 3.5 接口设计

共 15 个接口路径，JSON 交互，金额单位为分。

| 方法 | 路径 | 说明 | 鉴权 |
|---|---|---|---|
| GET | `/api/menu` | 菜单全量（含类目、规格、库存） | 否 |
| GET | `/api/orders/:id` | 顾客凭订单号查询进度 | 否 |
| POST | `/api/orders` | 下单：重算金额、校验库存、幂等 | 否 |
| GET | `/api/recommend/options` | 推荐的表单可选项 | 否 |
| POST | `/api/recommend` | 套餐推荐（一次返回） | 否 |
| POST | `/api/recommend/stream` | 套餐推荐（阶段事件流） | 否 |
| POST | `/api/nl-order` | 一句话点餐（一次返回） | 否 |
| POST | `/api/nl-order/stream` | 一句话点餐（阶段事件流） | 否 |
| POST | `/api/login` | 后台登录，下发会话 Cookie | 否 |
| POST | `/api/logout` | 退出登录 | 是 |
| GET | `/api/session` | 当前会话 | 是 |
| GET / POST | `/api/orders` | 商家订单列表 / 接单与状态流转 | 是 |

| GET / POST | `/api/stats`、`/api/stats/insight` | 经营看板数据与解读 | 是 |

# 4 意图控制策略

赛项要求重点阐述。本章说明人与 AI 的分工边界、上下文怎么组织、Prompt 怎么设计，以及如何在 AI 跑偏时把它拉回来。

## 4.1 协作方式

采用「人定边界、AI 填实现」。人的职责固定在四件事上，其余交给 AI：

| 人的职责 | 具体做法 | 仓库中的痕迹 |
|---|---|---|
| 定边界 | 先声明硬约束（零第三方依赖、Node ≥ 18、前端单文件、数据落 JSON），再让 AI 出方案 | 各 Prompt 首节、README 技术栈 |
| 定验收 | 每个迭代先写「怎样算完成」，再写代码 | `prompts/` 各篇的「验证」节 |
| 做取舍 | 对 AI 给的备选逐条否决并留理由 | `prompts/` 各篇的「取舍」表 |
| 复核 | 不接受「看起来对」，必须给出状态码、日志或截图 | 自测 73 项 + CI |

## 4.2 上下文管理

AI 跑偏的主因不是能力，是上下文给错。每次迭代开场固定投喂三类信息：

1. **硬约束**：如「服务端必须零第三方依赖」。这一条直接否决了 SQLite、Express、JWT 等一整套方案，避免后期回退。
2. **现状事实**：如「跟踪页当前只做了前端轮询」。用事实替代模糊描述，AI 才不会重复实现已有能力。
3. **受影响文件**：只喂需要改的文件与相邻接口定义，避免把整个仓库塞进上下文导致风格漂移。

## 4.3 Prompt 结构模板

凡是涉及多文件改动的任务，统一按五段式组织，避免「帮我做个后台」这种开放式指令：

```
【目标】一句话说明这次要交付什么
【现状】相关文件当前是什么状态、有哪些已知限制
【约束】不能引入什么、不能改什么、必须保持什么
【契约】接口形状、字段、状态码、错误文案
【验收】跑什么命令、期望看到什么结果
```

模板的价值在于把验收标准写进 Prompt 本身，AI 会围绕验收项组织实现，而不是堆功能。

## 4.4 迭代链

`prompts/` 下 9 条迭代记录，与提交历史一一对应。核心决策如下：

| 迭代 | 关键决策 | 被否决的方案与理由 |
|---|---|---|
| 01 订单落库 | JSON 单文件存储；服务端重算金额；下单扣库存 | SQLite（Node 18 不可用）；前端算价（金额可篡改）；不扣库存（后台改库存成摆设） |
| 02 登录鉴权 | Cookie + 内存会话；口令哈希后定时安全比较；按 IP 限速 | JWT（零依赖下要自实现 HMAC，收益低）；Basic Auth（无法主动登出） |
| 03 状态驱动跟踪 | 落事件链；5 秒轮询；终态停止 | SSE / WebSocket（状态变化是低频事件，握手与重连成本高） |
| 04 小程序端 | 原生 + TS strict；模块级状态；双端字段对齐 | uni-app / Taro（3 页规模编译与调试成本过高） |
| 05 AI 推荐 | 本地营养学模型 + 组合搜索；模型仅润色 | 直接调大模型生成套餐（不可复现、无法解释） |
| 06 日志与 CI | JSON Lines 结构化日志；9 类关键事件；脱敏 | 引日志框架（违背零依赖）；只打 `console.log`（无法按请求回溯） |
| 07 一句话点餐 | 模型输出固定 JSON；校验后本地筛选；逐级放宽 | 让模型直接推荐菜品（不可复算、无法解释） |
| 08 经营看板 | 纯 CSS 图表；数字服务端算好；模型只写建议 | 引图表库（违背零依赖）；让模型自己统计（必然算错） |

其中三条典型的完整 Prompt 链（提问 → AI 首版 → 纠偏 → 验收）见 `prompts/snapshots/`，分别是建仓排障、推荐引擎调参、大模型润色的数字约束。

## 4.5 纠偏与复核

AI 的产出不直接进主干，必须过三道闸：

- **语法闸**：`node --check` 与小程序 `tsc --noEmit`。
- **行为闸**：用 `curl` 打真实接口，核对状态码与响应体，覆盖正常路径与至少两条异常路径。
- **视觉闸**：headless 浏览器截图，确认页面确实渲染成预期样子，防止「接口对但界面崩」。

三道闸在 `prompts/` 的验证记录里逐条留痕。

## 4.6 约束清单

| 约束 | 来源 | 对实现的直接影响 |
|---|---|---|
| 零第三方依赖 | 部署环境不可控 | 路由、静态服务、Cookie 解析、原子写全部手写；代价是功能密度受限 |
| Node ≥ 18 | 评审可能用较老运行时 | 不使用 `node:sqlite` 等新 API |
| 前端单文件、免构建 | 评审要能双击查看 | 无打包工具、无框架，样式与逻辑内联 |
| 金额以「分」为整数 | 浮点误差不可接受 | 全部金额字段整数存储，展示层转换 |
| 模型不参与计算 | 结果必须可解释 | 推荐由本地算法产出，模型只改写语气 |

# 5 关键功能实现

## 5.1 订单闭环与状态机

顾客提交订单后，服务端按 `dishId + 数量 + 规格` 重新读取价格并重算金额，前端传的价格一概不认；随后校验估清与库存，写入订单并扣减库存，同时追加一条 `created` 事件。商家在后台接单、完成，每次状态变化都追加事件，顾客端轮询读取事件链渲染进度条，进入终态后停止轮询。

## 5.2 登录与鉴权

口令经 SHA-256 后以定时安全比较校验，通过后生成随机会话令牌，写进 `HttpOnly + SameSite=Lax` 的 Cookie；会话存内存 Map 并滑动续期 8 小时。同一 IP 连续 5 次失败锁定 60 秒，避免撞库。所有后台接口统一走鉴权中间件，未登录返回 401 而非静默失败。

## 5.3 AI 套餐推荐

分三步：

1. **算目标**：由性别、年龄、身高、体重、活动量与目标估算基础代谢与每日消耗，按单餐占比得出本餐的热量与蛋白预算。
2. **组合搜索**：在在售菜品中枚举组合并打分，目标函数兼顾蛋白达成、热量偏差与价格，蛋白超过目标 1.3 倍开始扣分，避免把「能加蛋白的都堆上去」当成个性化。
3. **约束校验与降级**：预算内无解时退化为「满足营养下限的最便宜组合」，并显式标注 `budgetRelaxed`，前端提示「预算内没有合适组合，已自动放宽」。

推荐结果附带偏差与理由，日志记录候选组合数、耗时与选中菜品，便于复核。典型规模为 674 个候选、2~6 ms。

## 5.4 一句话点餐

模型负责把自然语言转成固定 JSON 条件（热量上限、蛋白下限、价格上限、素食、忌口词），服务端校验后**在本地筛选**，而不是让模型直接报菜名。模型不可用或输出不合法时，退回关键词规则解析；命中为空时按「去掉最次要条件」逐级放宽，并把放宽了哪些条件告诉用户。

## 5.5 经营看板

订单聚合成当日单量、营业额、客单价、热销榜与热量分布，数字全部由服务端算好，前端用纯 CSS 绘制条形图，不引入图表库。解读文案优先由模型生成，失败退回模板，接口返回中标注来源是 `llm` 还是 `template`。

## 5.6 AI 响应状态可视化

两个 AI 入口都不是「点了等几秒突然出一屏结果」。服务端把处理拆成阶段事件，用 SSE 边算边推：

| 入口 | 阶段 | 展示内容 |
|---|---|---|
| 套餐推荐 | 解析身体指标 → 筛出在售菜品 → 组合搜索与打分 → 约束校验与优选 →（可选）模型润色 | BMR/TDEE/每日目标；在售与估清数量；候选数、耗时；热量偏差与蛋白达成 |
| 一句话点餐 | 解析意图 →（不可用时）规则兜底 → 本地筛选 → 条件逐级放宽 | 原话回显；识别出的条件；命中数；放宽项 |

两个设计约束：阶段中的数字全部来自真实计算，不是占位文案；前端只控制展示节奏（每阶段约 300 ms 最小间隔），否则时间轴会一闪而过。这一点在源码注释中已注明。流式不可用时前端自动退回一次性接口。

## 5.7 点餐搭档

点餐页右下角常驻一个入口，进去是能记住你的点餐搭档。它和「一次性推荐」的区别在于：**输入是真实订单，输出能直接变成购物车里的菜**。

**记忆。** 以订单手机号为键，落一份很轻的档案（目标、身高体重、忌口），其余全部从订单实时计算：本周单量、每餐平均热量与蛋白、蔬菜占比、最常点的菜、距上次点餐几天。没有打卡，也不需要额外汇入。

**主动建议。** 打开面板不等提问，先按规则算出该说什么，每条都带数字：蛋白缺口按「目标×0.75」判定并给出缺少的克数；近 7 天同一道菜达到 3 次提示重样；蔬菜占比低于 20% 提示加菜；连续 3 天以上有记录则给正反馈。判定全部在本地完成，模型不参与。

**对话。** 四类意图走规则匹配而非让模型自由生成：改忌口、改目标、复盘本周、按目标配一餐。改忌口会写入档案并在后续推荐中生效，这是「记忆」最直观的一条。配餐复用第 5.3 节的组合搜索，因此结论与直接点推荐完全一致。

**可视化。** 面向的是健身与减脂客群，他们判断「靠不靠谱」主要看数据能不能一眼读懂，所以面板以图表为主：

- **一句话结论**：角色用一句话讲清结论，例如「每餐平均 686 kcal，比目标高 32%，可以挑清淡一点的」。消费者只读这一句，下面的图全是佐证。结论按状态换配色：正常绿、超标橙、偏低蓝，配合角色的表情式气泡，形成可记忆的视觉锚点。
- **目标达成**：热量、蛋白、蔬菜三条横条，按「每餐均值 ÷ 你的目标」填充；低于 80% 用浅绿、80%~120% 用品牌绿、超过 120% 转橙，右侧给「686 kcal / 520」这样的原值与目标——颜色本身就传达了超没超，不再重复堆百分比。
- **近 7 天每餐热量**：七根柱状图，高度按当周最大值归一，红色虚线标出单餐目标，逐日数值标在柱顶，绿柱达标、橙柱超标；底部只留一行「6 天有记录 · 单餐最高 1200 kcal」，不写长句。
- **记忆标签**：本周单量、份数、最常点的菜、上次点餐距今几天，压缩成一行，不占版面。
- 图表全部用 CSS 绘制，未引入任何图表库；顶部吉祥物是三片叶芽的手写 SVG，带呼吸与眨眼动画。

口径统一：目标热量与蛋白是「每餐」口径，因此横条与柱状图都按单量求均值，不拿单餐目标去比日总量。

点餐搭档的回答同样走阶段事件流：读取记录 → 回顾近 7 天 → 比对目标 → 生成建议，进度直接显示在对话气泡里。

**与其他做法不同在哪。** 常见的健康类应用要求用户先填一套身体数据、再每日打卡，记忆由用户手工维护；本节的记忆直接来自本店的真实订单，用户不需要额外做任何事，且建议最终落成一个可点击的加购动作，而不是一份看完即弃的静态计划。

**边界。** 一切基于订单与档案，不采集体重秤、运动手环等外部数据；营养值仍是估算值；没有账号体系，换手机号即换记忆。这些限制写在 README 与本文第 9 章。

# 6 工程质量与安全

## 6.1 零依赖与原子写

服务端不使用任何第三方包，全部能力手写。写文件采用「临时文件 + 重命名」的原子替换，避免进程中断留下半个 JSON：先写 `*.tmp`，`fsync` 后 `rename` 覆盖目标文件。

## 6.2 输入校验与金额可信

所有入口参数按类型与长度校验，非法输入返回 400 与中文提示；金额相关的字段只接受整数分；菜品库存、价格在服务端二次读取，客户端提交的价格不参与计算。日志在落盘前统一脱敏手机号、口令、令牌与 API Key。

## 6.3 测试与持续集成

- **端到端自测**：`scripts/selftest.js` 按真实调用顺序跑 11 组、73 项检查，覆盖菜单、下单、扣库存、状态流转、鉴权、推荐、一句话点餐、看板、登出与日志脱敏。
- **持续集成**：每次 push 运行服务端语法检查、小程序 `tsc --noEmit` 与三个接口冒烟。

## 6.4 风险与限制

| 风险 | 影响 | 当前处理 |
|---|---|---|
| JSON 文件并发写 | 高并发下可能丢写 | 原子替换 + 单进程部署；订单量小，不构成实际瓶颈 |
| 会话存内存 | 进程重启后需重新登录 | 后台单账号，可接受；多实例部署前需换成外部存储 |
| 营养数据为估算值 | 推荐结果不能作为医学建议 | 数据文件与界面均标注「估算值」，不声称检测数据 |
| 未接支付 | 只能线下结算 | 明确列入本期不做，见 2.4 |

# 9 总结与展望

本作品把一个小微轻食门店的接单流程做成了可运行的系统：菜单单一数据源、下单前完成校验、订单状态可见、经营数据可读，并在此之上做了两个可解释的 AI 能力。工程上坚持零依赖与单机可跑，使评审无需准备环境即可在十分钟内跑通。

后续规划按优先级排列：补齐顾客标识以输出复购率；上线后按 8.5 的四个指标做两周实测；在资质齐备后接入微信支付与小程序上架。
